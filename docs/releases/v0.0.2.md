# LZY 0.0.2 — Correctness

A fix release, published the same day as 0.0.1.

**If you are on Windows with Python 3.9 or 3.10, please upgrade.** In 0.0.1 a
deep expression could kill the interpreter process instead of reporting an
error.

There are no language changes. Every 0.0.1 program still runs, and runs the
same way.

---

## What happened

0.0.1 was published with CI configured but never run — there had been no
repository for it to run against. The first run found a genuine crash within
minutes:

```text
say 1 + 1 + 1 + ...      # about 2000 terms
```

```
Windows fatal exception: stack overflow
```

Windows, CPython 3.9 and 3.10 only.

## Why it happened

Two mistakes compounding, both worth writing down because both are easy to
repeat.

**A comment in the test suite was wrong.** It said that left-associative
parsing made a long operator chain "a loop, not deep recursion". That is true
of *parsing* — the operator loop is iterative — and false of *evaluation*. The
tree gains one level per operator, and working it out later recurses once per
level:

| terms | parser recursion | tree depth |
|---|---|---|
| 10 | flat | 13 |
| 2000 | flat | 2003 |

`max_parse_depth` bounds parser recursion, so it never fired on the one shape
that mattered.

**`python_recursion_limit` had been raised to 20,000.** That does not create
stack. It only moves the point where CPython raises `RecursionError`, so on a
stack that cannot hold 20,000 frames it converts a catchable error into a
fatal crash. Windows gives the main thread 1 MB — roughly 1,000 frames on 3.9
and 3.10. CPython 3.11 stopped consuming C stack for Python-to-Python calls,
which is exactly why 3.11 and later were unaffected, and why local testing on
3.11 never saw it.

There was a second consequence, worth stating plainly: `max_call_depth = 400`
is documented and advertised — recursion is a headline feature with `fib`
examples — and it is several thousand Python frames. **It was never actually
reachable on Windows with 3.9 or 3.10.** The recursion tests did not catch
that only because the suite crashed at 55%, before reaching them.

## What was fixed

| Part | What it bounds | Why the others miss it |
|---|---|---|
| `max_ast_depth` = 5,000 | the tree the parser returns | `max_parse_depth` sees parser recursion, not the tree |
| `max_evaluation_depth` = 5,000 | total live nesting while running | many shallow calls each holding an expression open |
| 64 MB thread stack | the platform floor itself | limits mean nothing if the stack cannot hold them |

The tree walk is **iterative on purpose**: the check that prevents a stack
overflow must not be able to cause one. It runs at parse time, so `lzy check`
catches it too.

`max_call_depth` stays at 400 and still fires first for runaway recursion,
because "called itself too many times" is a better message than "too deeply
nested".

Past the limit you now get an ordinary LZY error:

```
This code nests too deeply for LZY to work through.

LZY handles up to 5,000 levels of nesting, and this reaches 8,003. A very long
chain of operators counts as nesting, so splitting it across several lines with
names for the parts will fix it.
```

## Also in this release

- All 150 `ruff` findings cleared; the CI lint job passes.
- `ruff` pinned to `>=0.16,<0.17`, so a new linter release cannot turn CI red
  on a branch that changed nothing.
- The version is declared once, in `lzy/__init__.py`; `pyproject.toml` reads
  it, so the package and its metadata cannot disagree. CI checks that the
  built wheel carries the right version.
- SECURITY.md claimed LZY "never crashes the process". That was false on
  Windows. The hardening table now lists the three new mitigations and names
  the crash that prompted them.

## Upgrading

```bash
pip install --upgrade lzy_lang-0.0.2-py3-none-any.whl
```

No changes to your programs are needed.

## Verification

Unlike 0.0.1, this release has a CI history behind it.

- **19/19 checks green**, including Windows 3.9 and 3.10 — the two that were
  failing.
- Tested on Ubuntu, macOS and Windows across Python 3.9, 3.10, 3.11, 3.12 and
  3.13.
- 1170 tests pass. Eleven are new and cover: the 2000-term chain, an
  8000-term chain erroring cleanly, `lzy check` catching it, the documented
  400-call depth actually being reachable, the evaluation-depth backstop, a
  deliberately tiny 256 KB stack still erroring rather than crashing, a
  platform that refuses stack sizing, and the global stack-size setting being
  restored.
- The wheel is installed into a clean virtual environment and run, in CI and
  by hand.
